# 00 · 扩展到底是怎么跑起来的

写给第一次做浏览器扩展的人。读完你应该能回答：我改的哪个文件，最后跑在浏览器的哪个地方。

## 1. 扩展就是一包静态文件

`pnpm build` 之后，`dist/` 里有一份 `manifest.json` 加一堆 js/html/png。Edge 打开这个目录，就等于加载了一个扩展。没有服务端、没有安装过程、没有「编译成原生程序」这一步。

`manifest.json` 是这张「身份证」，它声明了三件事：

1. **我能用什么能力**：`permissions`（storage、scripting、contextMenus…）。
2. **浏览器会自动在哪些页面注入我的脚本**：`content_scripts`（这里是所有 `http/https` 页面）。
3. **我的入口在哪**：`background.service_worker`、`action.default_popup`、`options_ui.page`。

## 2. 四个运行环境（这是最容易搞混的地方）

| 环境 | 文件 | 能做什么 | 不能做什么 |
|---|---|---|---|
| Service Worker | `dist/background.js` | 联网 fetch、用大部分 chrome API、监听菜单与快捷键 | 不能碰任何页面的 DOM，没有 `document`；闲置约 30 秒会被回收 |
| Content Script | `dist/content.js` | 读写所在页面的 DOM、监听选区 | **不能跨域 fetch**（受页面 CORS 限制）；不能用 `chrome.storage` 以外的很多扩展 API |
| 扩展页面 | `popup/`、`options/`、`learning/` | 完整的 React 界面、`chrome.storage`、`chrome.permissions`、`chrome.tabs` | 不能直接操作网页 DOM（要发消息给 content script） |
| 页面本身 | 你访问的网站 | 与扩展互不影响 | 看不到 content script 里的变量（隔离世界） |

所以本项目的分工是：**页面里发生的事情（划词、改 DOM）由 content script 做；一切网络请求由 Service Worker 做；界面在工具栏弹窗与设置页。**

## 3. 为什么 content script 不能直接联网

浏览器的安全模型里，content script 的 fetch 算「页面发起的请求」，要遵守目标网站的 CORS 规则。而扩展的 `host_permissions` 只对**扩展自己的页面和 Service Worker** 有效。

结论：翻译请求必须 `content script → 消息 → Service Worker → fetch → 回来`。这就是为什么 `src/core/providers/` 全部只在 background 里被使用。

## 4. 点一下图标，发生了什么

1. 你点工具栏图标 → 浏览器打开 `manifest.json` 里 `action.default_popup` 指定的页面（`src/popup/index.html`）。
2. 弹窗页面加载 React（`src/popup/main.tsx`）。
3. 你输入文字按 `Enter`（或点「翻译」）→ 弹窗 `chrome.runtime.connect({name:'yuyi'})` 建立 Port，发 `{kind:'translate', requestId, segments…}`。
4. Service Worker 的 `port.onMessage` 收到请求（`src/background/jobs.ts`）。
5. 读设置（`src/storage/settings.ts`）→ 解析引擎（`src/core/providers/registry.ts`）→ 查缓存（`src/core/cache.ts`）→ 调服务商。
6. AI 流式返回时，SW 边收边 `port.postMessage({kind:'delta'})`。
7. 弹窗的 `useJob`（`src/app/useJob.ts`）把 delta 拼到界面上。
8. 结束发 `done`，SW 同时写历史（`src/storage/history.ts`）。
9. 弹窗本身关掉就清空，但结果已经进了历史：重开弹窗，切到「历史」tab 能找到刚才这条。

## 5. 源码和 dist 的对应关系

构建脚本 `scripts/build.mjs` 跑了三次 Vite：

| 第几次 | 入口 | 产物 | 为什么单独构建 |
|---|---|---|---|
| 1 | `src/popup/index.html`、`options`、`learning` | `dist/{popup,options,learning}/index.html` + `dist/assets/*` | 普通网页打包，可以用 ESM、可以引 React |
| 2 | `src/background/index.ts` | `dist/background.js` | 单文件 ESM 的 Service Worker |
| 3 | `src/content/index.ts` | `dist/content.js` | content script **不支持 ESM**，必须打成 IIFE 单文件 |

`public/` 里的东西（manifest、图标）会原样拷进 `dist/`。改 manifest 也要重新 `pnpm build`。

## 6. 一个心智模型

把这四条想成四个房间，中间靠「消息」递话：

```
[网页 DOM] ←→ [content script] ←消息→ [Service Worker] ←fetch→ [翻译服务]
                                        ↕ Port 消息
                                   [弹窗 / 设置页]
```

任何跨房间的调用，都要问自己：这条消息谁发、谁收、请求 ID 是什么、失败怎么传回去。本项目把协议集中在 `src/core/messaging.ts`，就是为了不让这套东西散落在各处。
